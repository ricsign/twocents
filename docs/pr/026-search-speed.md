# PR #26 — perf: the room stops waiting on the web, and the itinerary stops searching twice

## The complaint

> "'BUILDING YOUR ITINERARY' is taking a bit too long, same as when the agent
> uses search functionalities. How can we improve the speed"

Two different stalls with the same cause: a web search sitting on the critical
path of something a person is watching.

## 1. The room no longer waits on a price check

`generateLine` ended on this:

    return { ...draft, offer: { ...scrubbed, feasibility: await checkOffer(scrubbed) } };

That `await` was between an agent finishing its line and the line being
spoken. `checkOffer` is an `offer-check` call with two server-side web
searches on it, so every proposal froze the town for the length of two
searches before a single word appeared. The check is also the only interesting
thing on that card — "a quick web search shows" is the product's own claim
about itself — so it was not a thing to cut.

**The check now runs beside the negotiation.** `startCheck` fires it when the
offer is drafted and nothing waits on it; the `speak` and `offer` frames go out
immediately, and the verdict arrives afterwards on a new frame:

    { type: "offer-checked", offerId, feasibility, sourced? }

A patch, not a row. It carries an offer id rather than a speaker because every
consumer's job is to find the card that is already on screen and fill in its
"checked · …" line and its search receipt — `useNegotiation`'s reducer maps
over `turns` and `offers`, the town's `Transcript` renders the same two fields
it always did, and `/api/negotiate` applies the same patch to the transcript
row it stores, so a session read back later still shows the verdict and its
links. (The route now also hangs the `offer` frame on its turn, which it never
did: a stored transcript had the sentence but not the card, and without the
card there is nowhere for a verdict to land.)

**Every verdict is still in hand before anything is decided.**
`findConvergedOffer` reads `feasibility?.bookable !== false`, so a missing
verdict is a room that can settle on a price the web says does not exist.
`joinChecks` awaits the outstanding checks once, at the end of the round loop,
after the rotation and before either convergence rule runs. That is the last
moment a verdict can change the answer, and it means the round pays for all
four searches at their slowest rather than for four searches in series.

Two ordering details are load-bearing. The offer is pushed onto `offers` in the
same synchronous step as its turn, before the `yield` hands control back to the
caller — a verdict landing across that suspension has to find both halves or it
patches the transcript and leaves the array `findConvergedOffer` reads stale.
And `applyCheck` records every verdict in a `verdicts` map, which the round loop
reads when it builds the turn: a check can answer while its own line is still
being regenerated by the repeat nudge, and at that moment there is nothing in
either array to patch. Between them the mechanism does not care which of the
two lands first.

`eventForViewer` returns the new frame untouched, and that was checked rather
than assumed. It is about an option that was said out loud: the offer went to
every viewer on its own frame already, the desk that produced the verdict is
handed an `Offer` and never a `Brief`, and the same "checked · …" line is on
the shared card all four people read.

The `speak` frame's `sourced` field is gone, because nothing can set it any
more — the receipt is built from a verdict, and at the moment a line is spoken
there is no verdict. Zod is the source of truth, so a field that can never be
populated does not stay in the schema.

**Saving.** The whole of the check, per proposal — call it 6–12s for two
searches, now 4–8s for one — comes off the gap between an agent finishing and
its line appearing, on every turn that proposes something. The seeded run puts
up two offers; a live judges' room puts up more. What is left is the
end-of-round join, which is one check's latency rather than the sum, and only
in the round where an offer was actually made.

## 2. A deadline sized for the check, not for a sentence

`offer-check` inherited `llmTimeoutMs()`, 20s, which is sized for a
two-sentence turn the room is waiting on. It now has its own ceiling of **10s**.
The penalty for missing it is `UNCHECKED`, which the transcript already renders
honestly as "Not checked against live prices." — so a slow search costing the
room nothing is strictly better than a slow search costing it twenty. Ten is one
search plus the emit with room to spare.

`MAX_SEARCHES_PER_OFFER` drops from **2 to 1**. The desk's own prompt is the
argument: rule 2 only lets it answer "not bookable" when the price is off by
roughly a third or more, and rule 3 tells it to leave an option it could not
price bookable. An all-in figure for a destination and a length of stay settles
both. The second search bought precision on `realisticPerPerson`, a field the
desk is already allowed to return null, at the price of a server-side round trip
the room used to sit through. Roughly halves the check.

## 3. The itinerary repair pass no longer searches

`verifySchedule`'s repair call was made with `maxUses: ITINERARY_MAX_SEARCHES`
— eight searches, the same as the first call — and 8000 tokens. It does not
need them. Every problem `checkAvailability` raises is a comparison between two
fields that are already in the draft it is handed back: an item's `startsAt`
against its own `opensAt`, `closesAt` and `closedDays`, or against the flight's
`arrivesAt` and `returnsAt`. The pass is re-timing things the first call already
found and priced.

`webSearch` is gone from that call, and `ITINERARY_REPAIR_MAX_TOKENS` is 6000 —
still comfortably a whole document, because the first rule it is given is to
return the whole document, minus the budget the searching call spent on deciding
what to query and reading results.

Two rules in `ITINERARY_REPAIR_SYSTEM_PROMPT` moved with it, because a prompt
that says "Search again where you need to" to a model with no search is a prompt
that lies to it. It is now told the hours are already recorded on each item and
to reschedule from those, and to move or drop a place that cannot work rather
than invent an unlooked-up replacement — which is what `applyUnresolved` does to
it anyway.

**Saving.** Up to eight searches on the repair pass, which only runs when the
first draft had a scheduling problem — but that is the common case, and it is
the slow half of a screen someone is watching a progress bar on. Call it 15–30s
when it fires.

## 4. The first itinerary call searches five times, not eight

Eight was one per day plus flights and beds. That reads the prompt as if each
day were an independent lookup, and it is not: the days share one destination,
and the three things the rules actually require the model to look up are the
flight (with departure, landing and return times), the bed (with check-in), and
real named places with their posted hours. The last is a destination-level
question — "what is open in San Juan and when" — whose results serve Tuesday and
Friday alike. Two structural searches plus three on the place.

The floor is set by a rule rather than by taste: the model is told to leave
`opensAt`/`closesAt` empty rather than invent them, so a budget too small to find
hours degrades to a document with unknown hours — honest, and checked as unknown
— rather than to a wrong one. Below about four it starts degrading the day
content, which is the part people read.

`ITINERARY_MAX_TOKENS` stays at 8000 and the doc comment now says why it must:
a tool call that runs out of room mid-object arrives as a schema failure, and
`build.ts` answers a schema failure with the canned itinerary. Shaving the
ceiling to save seconds would cost the whole live document. Slow beats canned.

**Saving.** Three searches, 6–12s.

## 5. The numbers are printed, not claimed

Four new `console.info` lines, in the house style of
`[negotiation] N round(s), …`:

    [negotiation] offer-check offer-cancun in 4310ms
    [negotiation] offer-check offer-cancun gave up after 10002ms
    [itinerary] repair pass in 8120ms
    [itinerary] built live in 41003ms: 28110ms model, 8120ms schedule check, 4773ms links and photos

The itinerary line is the one that settles arguments: it splits the build into
the model call, the schedule check and its repair, and the link and photo
fetches, so the next person tuning these constants can see which third they are
tuning instead of taking this document's word for it. The failing offer-check
is timed too, because the check that hits its deadline is the expensive one.

## Coverage

`offline-scenario.check.ts` gains `GatedProvider`, which holds every call of one
tag until it is released. `CountingProvider` can say how many calls happened and
how many overlapped; it cannot say that something reached the screen *while* a
call was outstanding, because the canned provider answers in microseconds. The
new check asserts that the first `offer` frame arrives with the check started,
unfinished and no `feasibility` on the offer; that every offer gets an
`offer-checked` frame and never before its own `offer` frame; and that the plan
the run settles on still carries a verdict, which is the join at the end of the
round doing its job.

`session-view.check.ts` adds the new frame to `PUBLIC_EVENTS`, so "the narrowing
left it alone" is asserted about it rather than assumed.

## Not changed

Redaction, the fairness maths, the negotiation's argument, `BEAT_WEIGHT` for the
spoken line, and the itinerary's visual design. The link verification and photo
fetching in `assemble` and `buildDay` were already parallel and were left alone.
The repair pass keeps `itineraryTimeoutMs()` — a 120s ceiling on a non-searching
call costs nothing unless the call is genuinely slow, and the fallback is
keeping the unrepaired draft.
